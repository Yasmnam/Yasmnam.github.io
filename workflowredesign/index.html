Case study five — Workflow design

Redesigning the workflow builder canvas, activity configuration and testing experience

ARKK, 2024–2025 — Enterprise data platform

Lead product designer — 4 initiatives, 15+ design review cycles. Platform: web app (desktop). Deliverables: handoff specs, component library.

Context

ARKK's enterprise data platform ran its workflow builder through a modal-based editor: a flat, vertical activity configuration stack layered on top of a canvas with limited visibility.

Across four initiatives and more than fifteen design review cycles, the editor moved to a full-screen canvas built on Foblex Flow — a third-party Angular library — with a structured activity configuration drawer and new workflow testing capabilities.

The problem

A modal-based editor that couldn't scale.

  1. The modal overlay sat on top of the canvas, obscuring the flow map underneath it.
  2. Activities had no grouping or ordering, which made complex configurations hard to navigate.
  3. The canvas was missing baseline controls — zoom, pan, multi-select.
  4. There was no keyboard navigation, and no undo or redo.

Foblex Flow — capability audit

The engineering team chose Foblex Flow, a third-party Angular library, as the foundation for the new canvas. Mapping every interaction it supported out of the box against the project's functional requirements split the design scope in two: what the library already handled, and what needed custom design and code.

Out of the box

  1. Node dragging and repositioning.
  2. Single-node selection.
  3. Basic viewport controls — zoom, pan, minimap.
  4. Fixed top and bottom connection ports.
  5. Auto-routed connector lines.

Needed custom design

  1. Node states for status, error and publish.
  2. Connection styling that reflected selection state.
  3. Multi-select, grouping and collapsible nodes.
  4. Search and filter across activities.
  5. A contextual canvas toolbar.
  6. The activity configuration drawer itself.

The audit shaped the entire scope of the redesign — separating what Foblex Flow could reliably do from what needed governance-level design and custom UI built on top of it.

Process

  1. Library audit. Mapped Foblex Flow's out-of-the-box capabilities early, to focus exploration on the genuine gaps.
  2. Layout exploration. Compared modal, wizard and drawer patterns for the activity configuration surface.
  3. Review cycles. More than fifteen review cycles across four initiatives, converging the scope at each stage.
  4. Handoff specs. Delivered per-initiative handoff pages with use cases, UI annotations and component specs.

Initiative one — workflow canvas redesign

Rebuilt the editor as a full-screen canvas.

  1. Activity nodes. Custom node designs carrying status, error and publish states.
  2. Connections. Status-coded connection styling, with contextual highlighting on selection.
  3. Canvas toolbar. Search, zoom, grouping and fit-to-viewport controls, added to the canvas itself.
  4. Page layout. Explored several layout concepts before settling on a full-screen canvas with a configurable side panel.

Initiative two — activity configuration drawer

Three layout patterns, one structural rebuild.

  1. Tabbed layout. Kept fields off-screen until needed, but gave nested fields nowhere to go.
  2. Accordion layout. Scaled well and kept sections visible collapsed, but made long sections feel overwhelming.
  3. Drill-down menu. Kept the main view uncluttered, but took too many clicks to reach related fields.

Structured drawer with header, body and footer — the existing flat stack redesigned into a header for name and description, a scrollable body for settings and configuration, and a footer for contextual actions. Built to extend to future activity types and services.

Design solution

Key design decisions

  1. Full-screen canvas. Replaced the constrained modal editor with a canvas that had room for the full complexity of a workflow.
  2. Structured drawer redesign. Reshaped a flat, scrolling configuration stack into clearly separated sections.
  3. Activity-first over canvas-first. Chose the orientation that matched how users already thought about their workflows, over the one that mirrored the canvas structure.
